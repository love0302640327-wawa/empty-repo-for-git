# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
3. 挑出 `status` 不是 `ok` 的菜
4. ★ 建議備貨量要不要再調整（例如：明天客人比較多的日子，要不要多備幾份？多備幾份？）：分成兩層寫，不能混在一起
   - **基礎建議（只看今天的資料）**：直接用盤點的 `suggest`，並寫出算式「賣出 ＋ 沒買到 ＝ 建議」驗算，例如 `10 ＋ 3 ＝ 13`。`suggest` 跟算式對不上，就停下來回報，不要做建議
   - **隔日調整（考慮明天的條件）**：只有使用者提供了明天的證據才調整，例如遊戲「預告」的天氣或事件、明天的宣傳費、星等變化。調整時要寫出依據和算式。沒有證據就寫「無隔日證據，不調整」，**不可以自己加固定百分比**（例如「一律多備 20%」）
5. ★ 同一樣菜連續幾天都缺貨或報廢過多，要怎麼提醒：同一樣菜**連續 2 天以上** `status` 相同（都是 `out`，或都是 `over`），就加一行「連續 N 天缺貨／報廢過多：第 a～b 天」，並列出每一天的備貨、賣出、報廢、沒買到。如果連續報廢過多、而且 `sold` 是 0，提醒「可考慮下架」，但只提醒，不替使用者決定
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
★ 我想多看一個欄位：可執行性檢查（判斷下一版完整備貨能不能執行）
  總份數：各菜份數相加的算式 ＝ … 份（上限 80）
  上架樣數：… 樣（上限 4）
  總成本：Σ(份數 × 成本) 的算式 ＝ … 元（成本取規則書「菜單」表）
  宣傳費：… 元（只能是 0、200、500）
  可用資金：前一天的 endCash ＝ … 元（第 1 天是起始資金 2,000 元）
  結論：總成本 ＋ 宣傳費 ≤ 可用資金、總份數 ≤ 80、樣數 ≤ 4 → 可執行
        缺任何一項資料 → 尚無法確認可執行性（缺：…）
下一版每天建議的備貨量：基礎建議與隔日調整分開列
```
