# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | ★ 【觀察】當天報廢份數、清潔費；報廢 16 份以上另加 50 元清運費（規則書）。【推測】備貨多於當天真正想買的人，或那樣菜當天的主要客人沒來、定價讓人買不起 | ★ 用盤點的「賣出 ＋ 沒買到」降低備貨；同一樣菜連續幾天賣得很少，考慮下架換別的菜 |
| 嫌太貴很多 | ★ 【觀察】哪一天、哪樣菜、幾位客人嫌太貴。【推測】定價超過客人剩下的預算；也可能是第一樣菜用掉太多預算，第二樣才買不起 | ★ 照 pricing-rules 心法 1，在可定價範圍內降價測試；先確認降價後少賺的錢能不能被多賣的份數補回來 |
| 想吃的沒上架很多 | ★ 【觀察】哪一天幾位客人說沒上架、想吃的是哪樣菜。【推測】菜單沒選到這群客人想吃的菜；每天最多只能上架 4 樣（規則書） | ★ 把人數多的客群想吃的菜換上架，換掉賣得最少的那樣；注意新上架的菜會不會是別的客人討厭的 |
| 因為討厭的菜不進門 | ★ 【觀察】哪一天幾位客人因討厭而不進門、是哪樣菜。【推測】上架了某群客人討厭的菜，整群人直接不進門，也不留評價（規則書） | ★ 比較「這群不進門的人可能帶來的收入」和「那樣討厭的菜當天的收入」，前者比較多就下架那樣菜 |
| 星等往下掉 | ★ 【觀察】哪一天星等從幾顆變幾顆、滿意與不滿各幾人。【推測】不滿（什麼都沒買到）的比例太高，或滿意（買到最想吃、價格 ≤ 建議售價）的比例太低（規則書星等表） | ★ 先減少什麼都沒買到的人：補缺貨、上架客人想吃的菜；價格拉回建議售價以下。星等下降會讓隔天來客變少，要一起考慮 |
| ★ 我自己發現的現象：宣傳後增加來客，但淨利未改善 | ★ 【觀察】先核對有宣傳與沒宣傳兩版：多出的收入、多出的備貨成本、宣傳費（200 或 500）、多出的清潔費。【推測】多出的收入小於宣傳費加上多出的成本；或多來的客人因缺貨、沒上架、嫌太貴而沒買 | ★ 核對完數字才改：多來的人沒買到 → 先補貨或調菜單再宣傳；多賣的收入不夠付宣傳費 → 改回不宣傳或改用 200 元 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
